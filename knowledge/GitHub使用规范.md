# GitHub 使用规范：人指挥，AI 操作

这套规范面向 **完全不懂 Git / GitHub 的普通用户**。

核心原则只有一句：

> **用户表达目的，不负责 Git 操作；AI 理解目的并完成 Git / GitHub 全流程。**

用户不需要记住 `git add`、`git commit`、`git pull`、`git push`、分支、rebase、merge 等命令。

---

# 第一部分：人应该怎样告诉 AI

## 1. 不要告诉 AI“执行什么 Git 命令”，告诉 AI“你想得到什么结果”

| 你的诉求 | 直接对 AI 这样说 | AI 应该自动完成 |
|---|---|---|
| 保存今天的修改 | `把我今天改的这些内容保存好并同步到 GitHub。` | 检查修改 → 确认内容 → commit → push → 验证 |
| 新增一篇知识 | `帮我把这份内容整理成长期知识放进知识库。` | 查重 → 整理 → 选择目录 → 写 Markdown → commit → push |
| 丢进一个 PDF/Word/PPT | `帮我处理这个文件，原文件保留，把有价值的内容整理进知识库。` | 保存原件 → 转换阅读层 → 提炼 → 归类 → commit → push |
| 不知道文件放哪 | `这个东西我不知道应该放哪里，你帮我处理。` | 先放 inbox → 理解内容 → 判断归属 → 必要时询问 |
| 修改已有知识 | `把这条新信息补充到我以前关于 XXX 的知识里。` | 搜索旧知识 → 优先更新旧文件 → 保留来源 → commit → push |
| 找以前的内容 | `我以前有没有记录过 XXX？帮我找出来。` | 搜索仓库 → 返回最相关内容和位置，不制造重复文件 |
| 撤销刚才的修改 | `刚才改错了，帮我恢复到修改前。` | 检查 Git 历史/工作区 → 选择安全恢复方式 → 验证 |
| 看今天改了什么 | `告诉我今天这个知识库改了什么。` | 查看 diff / commits → 用普通话总结变化 |
| 建一个新主题 | `我准备长期研究 XXX，帮我建立合适的位置。` | 判断是 area / knowledge / project → 创建最小结构 |
| 开始一个项目 | `我要开始做 XXX，这件事预计做完就结束。` | 创建 project → 写目标/状态 → 后续跟踪 → Git 保存 |
| 项目结束 | `这个项目做完了，帮我收尾。` | 提炼可复用知识 → 更新 records → 项目移入 archive → commit |
| 同步另一台电脑的变化 | `帮我同步最新知识库。` | 检查本地未提交修改 → 安全 pull → 处理冲突 → 验证 |
| 出现冲突 | `GitHub 提示冲突了，你处理一下，不要丢东西。` | 读取双方内容 → 尽量合并 → 不确定时问用户 → 验证后提交 |
| 查看历史版本 | `这篇文章之前是什么样？` | 查看文件 Git 历史 → 找到版本 → 给用户比较 |
| 恢复误删文件 | `我之前删掉的 XXX 能恢复吗？` | 从 Git 历史定位 → 恢复 → 验证 → commit |
| 整理 inbox | `帮我把 inbox 清一下。` | 扫描 → 去重 → 分类 → 提炼 → 保留无法判断项 → commit |
| 大批量整理 | `帮我整理这些文件，但不要丢任何原始内容。` | 先做状态检查和计划 → 分批处理 → 保留原件 → 小提交 |
| 我不想管 Git | `后面的 Git 你自己维护，我只看结果。` | AI 全程管理状态、提交、同步和异常处理 |

## 2. 用户只需要掌握 4 种表达

### 我要新增

```text
帮我把 XXX 放进知识库。
```

### 我要修改

```text
把 XXX 更新到我已有的 XXX 内容里。
```

### 我要找东西

```text
帮我找一下我以前关于 XXX 的内容。
```

### 我要恢复

```text
刚才弄错了，帮我恢复，不要丢其他内容。
```

这已经足够覆盖绝大多数日常使用。

# 第二部分：AI 应该怎样帮助人类使用 Git

## 1. AI 的定位

AI 是 Git 操作员和知识库管理员。

用户是决策者。

正确关系：

```text
用户：说目标
  ↓
AI：理解目标
  ↓
AI：检查仓库
  ↓
AI：完成文件操作
  ↓
AI：检查差异
  ↓
AI：Git 提交与同步
  ↓
AI：告诉用户结果
```

不要反过来要求用户先学习 Git，再使用知识库。

---

## 2. 每次操作前，AI 必须先检查

至少检查：

```bash
git status
git branch --show-current
git remote -v
```

涉及远程同步时，还应确认：

- 当前工作区有没有未提交内容。
- 当前分支是否正确。
- 远程仓库是否正确。
- 是否可能覆盖别人或其他设备的修改。

**先保护用户已有内容，再追求操作速度。**

---

## 3. AI 不应该让普通用户做什么

正常情况下，不要对用户说：

```text
请运行 git add .
请运行 git commit
请运行 git pull --rebase
请解决冲突后再 push
请创建 SSH Key
请配置 credential helper
```

如果 AI 有终端权限，这些都应该由 AI 自己完成。

只有出现以下情况时才需要用户参与：

- 浏览器登录 GitHub。
- 输入验证码。
- 系统权限确认。
- 用户名/邮箱等 AI 无法推断的信息。
- 高风险删除、覆盖或无法判断的冲突。

即使需要用户参与，也只告诉用户当前必须完成的一个动作。

---

## 4. 提交规则

一次提交应该对应一个清晰目的。

好的提交：

```text
knowledge: add GitHub beginner workflow
inbox: organize imported documents
project: update personal website plan
records: add August decision log
chore: initialize knowledge environment
```

不好的提交：

```text
update
修改
123
save
```

不要为了“提交次数少”把几十件无关的事情塞进一个 commit。

也不要每改一个字就创建一个无意义 commit。

---

## 5. Push 规则

普通知识更新完成后，AI 可以自动 push。

Push 前必须：

1. 确认 commit 成功。
2. 确认远程地址正确。
3. 确认没有明显敏感信息。
4. 如果仓库是 Public，对新加入的个人数据进行额外检查。

Push 后应验证远程同步成功，而不是只根据命令退出码假定完成。

---

## 6. Pull / 同步规则

用户说“同步一下”时，AI 不应直接粗暴执行可能覆盖本地修改的命令。

正确顺序：

```text
检查本地修改
  ↓
有修改？先保护
  ↓
获取远程状态
  ↓
判断是否存在分叉
  ↓
安全合并
  ↓
验证内容
  ↓
必要时提交并 push
```

用户的本地未提交内容永远不能因为“同步”被静默丢弃。

---

## 7. 冲突规则

出现冲突时，AI 的目标不是“让 Git 变绿”，而是 **保证知识不丢失**。

AI 应：

1. 读取冲突双方内容。
2. 判断是否能无损合并。
3. 可以无损合并时直接处理。
4. 两边语义冲突但都可能正确时，同时保留并明确标记。
5. 涉及用户真实意图时，向用户说明差异并让用户决定。
6. 解决后重新检查整个文件。
7. 再提交和同步。

AI 不得为了快速消除冲突直接选择 `ours` 或 `theirs` 覆盖另一方。

---

## 8. 删除规则

普通用户说“删掉这个”时，AI 先理解用户是在说：

- 从当前目录移走？
- 归档？
- 删除生成的临时文件？
- 永久删除原始资料？

知识库默认：

```text
失效内容 → archive
```

而不是永久删除。

原始文件、重要知识、大量文件的永久删除必须先得到用户明确确认。

Git 历史可以恢复内容，但不能把“可以恢复”当作随意删除的理由。

---

## 9. 恢复规则

用户要求恢复时，AI 先确定恢复范围：

- 一个文件。
- 一次修改。
- 一个 commit。
- 整个仓库。

然后选择影响范围最小的恢复方法。

禁止为了恢复一个文件而粗暴重置整个仓库。

恢复完成后：

1. 检查其他用户修改是否仍存在。
2. 给用户说明恢复了什么。
3. 必要时创建新的恢复提交。

---

## 10. 分支规则

普通用户日常维护个人知识库，默认使用 `main` 即可。

不要因为“Git 最佳实践”强迫普通用户理解复杂分支模型。

只有以下情况才考虑临时分支：

- 大规模目录重构。
- 批量自动整理。
- 高风险内容迁移。
- 实验性自动化脚本。

即使使用分支，也由 AI 管理，用户只需要批准最终结果。

---

## 11. 敏感信息规则

AI 在提交前应特别检查：

- 密码。
- API Key。
- Access Token。
- 私钥。
- `.env`。
- 身份证件。
- 银行信息。
- 私人合同。
- 不适合公开的个人资料。

发现疑似凭证时：

1. 暂停 push。
2. 告诉用户发现了什么风险。
3. 将敏感文件加入忽略规则或移出仓库。
4. 如果秘密已经进入 Git 历史，按泄露事件处理，而不是只删除当前文件。

---

## 12. AI 给用户的最终反馈必须说人话

不要只回复：

```text
commit 3f9ab1 pushed to origin/main
```

应该回复类似：

```text
已经处理完成：
- 把你刚才的资料整理到了 AI 知识目录。
- 原文件保留，没有删除。
- 已保存一个版本并同步到 GitHub。
- 当前没有冲突，也没有未保存修改。
```

必要时可以附 commit，但 Git 术语不应该成为主要信息。

---

# 最终原则

**Git 是知识库的底层保险，不是用户的工作。**

普通用户的正确使用方式不是：

```text
学习 Git → 理解 GitHub → 学会命令 → 再管理知识
```

而是：

```text
告诉 AI 想做什么
       ↓
AI 管文件 + Git + GitHub
       ↓
用户只看结果、做决定
```

这也是本知识库长期运行的默认交互方式。
