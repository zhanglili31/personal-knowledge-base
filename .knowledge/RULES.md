# AI Knowledge Management Rules

本文档定义 AI 如何管理本仓库。优先级高于目录习惯和自动化脚本。

## 1. 总原则

- 用户输入优先，AI 不得为了“整洁”阻碍记录。
- 不确定归属时放入 `inbox/`，不要强行分类。
- 优先更新已有知识，不重复创建近似内容。
- 原始文件必须保留；转换后的 Markdown 只是 AI 阅读层。
- 所有自动整理必须可追溯、可回滚。

## 2. 内容归类

### inbox/
用于未处理内容。任何无法立即判断归属的内容都先留在这里。

### projects/
有明确目标、开始时间或结束条件的事项。

### areas/
长期持续负责、不会因为某个项目结束而消失的领域，例如健康、财务、职业、家庭。

### knowledge/
经过提炼、未来可重复使用的知识、方法、结论和经验。

### records/
事实型历史记录，例如决策、会议、复盘、重要事件、时间线。

### sources/
原始资料，包括 PDF、DOCX、PPTX、XLSX、图片、音频、网页快照等。

### archive/
已完成、不活跃但仍需保留的内容。

## 3. 文件处理规则

当用户放入非 Markdown 文件时：

1. 保留原文件。
2. 计算或记录可用于去重的文件标识。
3. 使用合适的转换工具生成 AI 可读文本；优先支持 MarkItDown。
4. 生成内容放入 `.knowledge/generated/`，不得覆盖原文件。
5. AI 根据转换结果建立摘要、索引和关联。

如果转换失败：

- 不删除原文件。
- 标记转换失败状态。
- 保留错误原因，允许后续重新处理。

## 4. 去重与更新

创建新知识前，AI 应先检查是否已有同主题文件。

若已有：

- 优先补充、修正、合并旧文件。
- 保留重要来源和时间信息。
- 对互相冲突的结论并列记录，不擅自抹掉旧结论。

只有在主题明显不同或旧文件过于庞大时才新建文件。

## 5. 命名规则

- 文件名直接表达内容，不使用 `note1.md`、`misc.md` 等无意义名称。
- 人类可读优先，不强制英文。
- 避免日期作为唯一名称；日期更适合记录类内容。
- 同一目录保持稳定命名习惯，不因为 AI 偏好频繁重命名。

## 6. Markdown 内容规则

长期知识建议包含：

```yaml
---
created: YYYY-MM-DD
updated: YYYY-MM-DD
status: active
---
```

正文优先写：

1. 当前结论
2. 原因或证据
3. 实际用途
4. 来源

不要为了形式强制补齐空章节。

## 7. AI 的权限边界

AI 可以自动：

- 新建普通知识文件
- 更新已有 Markdown
- 归类 inbox 中的低风险内容
- 创建索引和转换结果
- 执行常规 Git add / commit

AI 不应自动：

- 删除用户原始文件
- 覆盖原始二进制文件
- 大规模重命名或移动目录
- 删除历史知识
- 解决含义不明确的冲突
- 把敏感信息推送到公开远程仓库

上述高风险操作应先请求用户确认。

## 8. Git 规则

Git 是底层版本系统，不应成为普通用户的操作负担。

AI 应：

- 每次整理形成逻辑清晰的小提交。
- Commit message 说明做了什么，而不是写 `update`。
- 操作前检查当前状态，避免覆盖用户未提交工作。
- 冲突时优先保护双方内容，不强制覆盖。
- 遇到异常立即停止破坏性操作。

建议提交示例：

```text
knowledge: add notes about personal finance
inbox: organize imported AI documents
records: add 2026-08 project decision log
```

## 9. 长期维护规则

知识库应保持低维护成本：

- 平时允许 inbox 暂时混乱。
- 定期清理 inbox，而不是要求实时分类。
- 项目结束后，将可复用结论沉淀到 knowledge，再归档项目。
- 失效内容优先标记或归档，不直接删除。
- 不建立需要用户持续手工维护的复杂标签体系。

## 10. AI 生成内容

AI 回答不等于知识。

AI 生成内容只有在满足以下条件后才能进入 `knowledge/`：

- 明确用户问题或主题。
- 已提炼出可复用结论。
- 能区分事实、推断和建议。
- 重要事实尽量保留来源。

原始长对话默认不直接进入长期知识区。
